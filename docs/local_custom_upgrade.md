# 本地定制升级记录

这份文档只记录**本地二次开发内容**，目的是方便以后同步上游 `SiverKing/SiverWXbot_plus` 时快速核对、补回和验收。

## 当前定制概览

本地定制名称：私聊连续消息合并回复

目标：
- 解决对方连续拆开发多句时，机器人每条都立刻回复、显得机械的问题
- 让机器人在私聊里先等待一小段时间，合并理解后再回复
- 尽量把改动收敛在核心文件，减少以后合并上游的冲突面

本次定制只影响：
- 私聊普通 AI 自动回复

本次定制明确不影响：
- 群聊自动回复
- 管理员命令
- 群/私聊关键词固定回复
- 图片识别消息
- Web 面板字段与页面

## 修改文件

本次本地定制实际修改了这些文件：

1. `wxbot_core.py`
2. `config/config.json`

说明：
- 核心逻辑都在 `wxbot_core.py`
- `config/config.json` 只是补了默认配置项
- 没有改 `web_server.py`、`templates/`、管理员命令

## 新增配置项

以下字段为本地定制新增，默认写在 `config/config.json`：

```json
{
  "chat_merge_reply_switch": true,
  "chat_merge_wait_seconds": 6,
  "chat_merge_max_wait_seconds": 18,
  "chat_merge_max_messages": 5,
  "chat_merge_delay_min": 1,
  "chat_merge_delay_max": 3
}
```

字段说明：
- `chat_merge_reply_switch`
  - 是否开启私聊连续消息合并回复
- `chat_merge_wait_seconds`
  - 尾条消息后的静默等待秒数
  - 每来一条新消息都会重置这段等待
- `chat_merge_max_wait_seconds`
  - 同一批消息最长累计等待时间
  - 到达后即使对方还在断续发送，也先触发一次回复
- `chat_merge_max_messages`
  - 单批最多合并多少条消息
  - 达到上限后立即回复
- `chat_merge_delay_min`
  - 合并回复发送前的最小延迟秒数
- `chat_merge_delay_max`
  - 合并回复发送前的最大延迟秒数

说明：
- 这套延迟只用于“合并后的私聊回复”
- 它不复用原来的全局 `reply_delay_min/reply_delay_max`
- 目的是避免和你原本的 `5~60` 秒发送延迟叠加得太慢

## 核心实现说明

### 1. 入口位置

私聊普通 AI 回复入口仍在 `wxbot_core.py` 的 `process_message()`。

当前逻辑变为：
- 如果消息适合进入合并缓冲，就先入队，不立即调用 AI
- 如果消息不适合进入合并缓冲，先尝试把该会话已缓冲的文本批次 flush，再走原来的即时处理逻辑

### 2. 新增的私有方法

本地定制新增了以下私有方法：

1. `_should_batch_private_message`
2. `_enqueue_private_batch`
3. `_flush_private_batch`
4. `_build_batched_private_input`
5. `_trim_batched_history_tail`

职责说明：
- `_should_batch_private_message`
  - 判断当前私聊消息是否应该参与合并
- `_enqueue_private_batch`
  - 将消息放入按会话分组的缓冲区
  - 重置静默计时器
  - 在达到阈值时立即触发 flush
- `_flush_private_batch`
  - 真正执行批量回复
  - 重新按会话名获取聊天窗口，而不是复用旧窗口对象
- `_build_batched_private_input`
  - 将多条消息组织成一次 AI 输入
  - 使用“编号列表 + 合并理解”的提示格式
- `_trim_batched_history_tail`
  - 从记忆尾部移除本批已缓冲消息
  - 避免同一批内容同时出现在 `history` 和当前 `message` 中，被 AI 看两遍

### 3. 合并触发规则

当前实现固定为以下任一条件触发：

1. 最后一条消息后静默满 `6` 秒
2. 同一批累计等待超过 `18` 秒
3. 同一批消息达到 `5` 条
4. 同一会话来了不适合继续合并的消息，需要先把已有文本批次 flush

### 4. 什么消息会参与合并

默认会参与合并的消息：
- 私聊普通文本
- 语音转文字后的文本
- 不含图片路径的普通引用文本

默认不会参与合并的消息：
- 图片消息
- 引用图片消息
- 命中私聊关键词固定回复的消息
- 群聊消息
- 已暂停私聊自动回复时收到的消息

### 5. AI 输入格式

当前不是简单把多条消息直接拼起来，而是使用下面这种结构喂给 AI：

```text
同一用户短时间连续发送了以下几条消息，请合并理解并给出一条自然、聚焦的回复。
不要逐条机械分别作答，也不要重复用户原话。
会话：某个聊天窗口
消息列表：
1. 第一条
2. 第二条
3. 第三条
```

这样做的目的：
- 明确告诉模型“这是一批连续输入”
- 避免模型逐条答题式回复
- 更容易得到像真人一样的整合回答

### 6. 发送链路复用

批量回复没有另外造一套发送系统，而是继续复用原有私聊发送链路：

- 接口错误固定回复
- 拆分多条回复
- 超长文本分段发送

唯一额外区别：
- 合并后的回复使用 `chat_merge_delay_min/chat_merge_delay_max`
- 不走原来的全局 `reply_delay_min/reply_delay_max`

## 以后升级时重点看哪里

如果以后从上游拉新版本，优先检查这些位置是否被上游改过：

1. `wxbot_core.py` 中的 `WXBotConfig`
2. `wxbot_core.py` 中的 `process_message()`
3. `wxbot_core.py` 中的 `wx_send_ai()`
4. `wxbot_core.py` 中的 `stop_wxbot()`

原因：
- 这几个点是本地定制真正挂载进去的地方
- 上游如果改了私聊消息处理、发送逻辑、配置加载，这里最容易冲突

## 推荐升级流程

建议以后按这个顺序升级：

1. 先备份当前目录中的 `config/` 和 `memory/`
2. 先把上游最新版本同步到本地 `main`
3. 再把本地定制分支 rebase 或 merge 到新的 `main`
4. 如果 `wxbot_core.py` 冲突，优先对照本文件逐项补回
5. 合并完成后，检查 `config/config.json` 中 6 个 `chat_merge_*` 字段是否仍存在
6. 最后进行手工回归验证

## 建议保留的分支策略

推荐长期保持下面这种结构：

- `main`
  - 尽量保持接近上游最新稳定版本
- `codex/private-chat-batch-reply`
  - 放你的本地定制

如果以后你还有别的定制功能，建议继续拆成独立分支或独立提交，不要把所有本地改动混成一团。

  - 指向原作者仓库 `SiverKing/SiverWXbot_plus`

## 手工回归清单

每次升级合并后，至少手测下面这些场景：

1. 同一私聊 6 秒内连续发 3 句
   - 预期：只回复 1 次，内容围绕三句合并后的语义
2. 同一私聊两句之间超过 6 秒
   - 预期：保持原来一条一回
3. 连续发到第 5 句
   - 预期：立即触发一次统一回复
4. 文本批次还没 flush 时又来关键词消息
   - 预期：先 flush 文本批次，再走关键词固定回复
5. 文本批次还没 flush 时又来图片消息
   - 预期：先 flush 文本批次，再走原有图片逻辑
6. 已开启“拆分多条回复”时
   - 预期：批量回复仍可继续拆分发送
7. 批次等待期间手动暂停私聊自动回复
   - 预期：该批次不补发
8. 打开 Web 面板保存一次普通配置
   - 预期：`chat_merge_*` 字段仍保留在 `config/config.json`
